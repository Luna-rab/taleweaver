# Image 集約の設計判断

## 前提

- 今、画像を書き換えるのは同期だけ。今後、ほかの集約から参照され、API から作成・削除される見込みがある。そのため画像は何の画像かを持たず、使う側が画像の id を持って参照する。
- 利用者がアップロードした画像は、取得元の ETag を持たない。

## 取得と保存の分担

| 誰が        | 何をする                                                                                               |
| ----------- | ------------------------------------------------------------------------------------------------------ |
| application | 取得元から画像を取得する（保存済みなら ETag を付ける）。結果をコマンドで集約に渡す                     |
| Image 集約  | 取得した結果から、登録・差し替え・変更なし・拒否を決め、新しいファイルの置き場所（storageKey）を決める |
| application | ファイルを storageKey に置き、DB に保存する。差し替えなら、保存した後に古いファイルを消す              |

集約に取得させないのは、取得したファイルを集約が受け取ると、それをイベントに載せて application に返すことになるため。

## 差し替えは新しいキーに置く

同じキーに上書きすると、DB の保存に失敗したときにファイルと行が食い違う。取得元は `max-age=14400` を返すので、配信先のキャッシュにも古い絵が残る。

## 取得元の場所と ETag

- 取得元の場所は、エディションの面の `imageSourcePath` だけが持つ。ETag は画像が持つ。
- 分けて持つのは、事実の出どころが違うため。ETag は保存したファイルについての事実で、パスは取得元がカードについて返す事実。
- 取得元の場所が変わったら（`imageSourcePath` の変わった `CardEditionRevised` が出る）、ETag を付けずに取得し直す。前の場所で受け取った ETag は、新しい場所の絵の版を表すとは限らない。

## まだ作らないもの

- 画像を取得し直す処理。
- 画像を消すコマンド。今は画像が使われなくなる経路がない（エディションの面は取り下げても残り、面の組も変わらない）。アップロードの機能と一緒に作る。
- アップロードのコマンド。
